# Direct-Pod write oracle

The oracle measures whether more than one Postgres instance accepts a write at
the same instant. Every canonical write goes to a literal Pod IP, through one
dedicated pgx connection per node. Acknowledged writes and commits recovered
from durable rows both count as writers. The detector is independent of
Services, Pod role labels, operator status, and Patroni's claimed role.

The oracle does not choose a primary, promote Postgres, repair a node, write a
Patroni or Kubernetes authority object, or prevent data loss. An
`ACKED_WRITE_LOST` result is a durability finding and remains separate from the
split-brain verdict. A pass also does not prove that every possible failure has
been explored; it certifies only the sampled run represented by its complete
artifact bundle.

This PoC is a walking skeleton. Its manifests and the invariants it validates
are intended to become target state generated by the CloudNativePatroni
operator. They are not a substitute for operator integration.

## Build and test

From this directory:

```text
go test ./...
go vet ./...
go build ./cmd/oracle
```

Replay uses the production detector path:

```text
go run ./cmd/oracle replay --fixture testdata/fixtures/dual-commit-run
go run ./cmd/oracle replay --fixture testdata/fixtures/clean-run
go run ./cmd/oracle replay --fixture testdata/fixtures/indoubt-run
```

The expected exit codes are 1, 0, and 2 respectively.

## Credentials

There is intentionally no password flag. `run` reads either
`CNPATRONI_CHAOS_PASSWORD_FILE` or `CNPATRONI_CHAOS_PASSWORD`. Bootstrap also
reads either `CNPATRONI_SUPERUSER_PASSWORD_FILE` or
`CNPATRONI_SUPERUSER_PASSWORD`. File and value forms are mutually exclusive.

## Deployment notes

The example Pod in `../chaos/deploy/oracle-pod.yaml` is deliberately explicit
and must be edited for the namespace, scope, expected Pod names, context,
scenario environment value, image, and duration of a run. It pins the example
image to `0.1.0`, schedules the
oracle on the control-plane node, and grants the oracle ServiceAccount only
`get`, `list`, and `watch`.

The checkpoint timeline stored by the canonical insert can lag immediately
after promotion. It is forensic data, not detector input. The database node's
`clock_timestamp()` is also forensic only; all ordering uses the oracle's
monotonic clock.
